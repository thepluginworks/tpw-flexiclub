# Shared Plugin Framework – System Page Protection Contract

**Status:** Authoritative  
**Applies to:** shared-framework system pages, private shortcode-backed front-end screens, and automatic page-list protection
**Audience:** Developers, Maintainers, QA

## 1. Purpose

This contract defines how the shared plugin framework protects private iLungu™ Club front-end pages from accidental exposure in public navigation while preserving route-based access control.

The protection model is layered:

1. identify known private iLungu Club pages
2. exclude them from logged-out automatic page listings generated by WordPress menu and page-list APIs
3. enforce direct access separately in the shortcode, router, or module that owns the page

Menu hiding is a discoverability safeguard. It is not a security boundary.

## 2. Scope

This contract covers:

- registered iLungu Club system pages managed through `TPW_Core_System_Pages`
- known private shortcode-backed pages that are not yet first-class registry rows
- logged-out automatic page-list output produced by WordPress core APIs

This contract does not cover:

- arbitrary site-owned custom theme queries that ignore WordPress page-list and menu APIs
- post-status changes as a privacy mechanism
- forced rewriting of explicit site-owned navigation menus, except the Core-managed iLungu Club Members Menu

## 3. Page Classification

### 3.1 Registered system pages

Core identifies registered system pages through the `TPW_Core_System_Pages` registry and stores lightweight page metadata when a page is created or rediscovered.

Current metadata markers:

- `_tpw_system_page_slug` — the registered system-page slug
- `_tpw_system_page_plugin` — the owning plugin identifier when known
- `_tpw_exclude_from_public_page_menu` — whether Core should hide the page from logged-out automatic page listings

### 3.1 Canonical Path Ownership And Collisions

The registry owns a canonical path only when the page is explicitly mapped in
`tpw_core_system_pages`, or when it carries both `_tpw_system_page_slug` and the
registered `_tpw_system_page_plugin` marker. A matching shortcode or slug alone
is not ownership evidence.

When provisioning or recreating a canonical System Page, Core creates the
requested path only when it is free. If another WordPress Page already occupies
that path without the ownership evidence above, Core returns a conflict and does
not adopt, publish, rewrite, mark, or map that page. Core also rejects a
WordPress-generated `-2` fallback rather than treating it as canonical.

Existing explicit mappings remain valid until an administrator deliberately
unlinks, recreates, or reassigns them. Consumer plugins must register and ensure
their System Pages through `TPW_Core_System_Pages` rather than duplicating slug
lookup or page-creation logic.

### 3.2 Private shortcode-backed pages outside the registry

Some iLungu Club pages may still be identified by shortcode or fallback slug rather than by a formal registry row.

Current Core-owned member and admin-style routes such as `manage-members` and `noticeboard` are now expected to be registered through `TPW_Core_System_Pages` while keeping shortcode-level direct-access enforcement.

## 4. Layered Protection Model

### 4.1 Identification layer

Core must be able to identify known private iLungu Club pages without relying on theme markup.

Current implementation uses:

- the System Pages registry for registered slugs
- persisted post meta for created or rediscovered pages
- shortcode or slug fallback discovery as a compatibility path when an expected page is not yet stored as a canonical mapping

### 4.2 Logged-out automatic page-list protection

For logged-out visitors, Core must filter known private iLungu Club pages out of WordPress-generated automatic page listings.

Current protected API families:

- classic page-list rendering via `wp_list_pages` / `wp_page_menu`
- block-theme `core/page-list` rendering, including navigation fallback paths that call `get_pages()`

Current implementation points:

- `wp_list_pages_excludes` for classic page-list output
- `get_pages` for block page-list rendering, scoped to automatic page-list contexts rather than all page queries

This contract is API-oriented, not theme-oriented. A future theme that uses the same WordPress automatic page-list APIs should inherit this protection without a theme-specific patch.

### 4.3 Direct access protection

Direct access protection must be enforced separately by the page owner.

That means:

- shortcode render callbacks
- route controllers
- POST handlers
- AJAX handlers
- protected file-serving endpoints

must each enforce their own login and permission rules.

Core must not treat menu hiding as sufficient protection.

### 4.4 Explicit navigation menus

Core does not rewrite arbitrary site-owned navigation menus to remove private links.

Rationale:

- explicit menus are editorial/site configuration, not automatic fallback output
- removing items from arbitrary menus would be a high-risk silent behaviour change across themes and sites

Exception:

- the iLungu Club Members Menu is a Core-managed menu surface and may be seeded or repaired by Core

If a site owner deliberately places a private iLungu Club URL in an explicit menu, direct access protection must still block logged-out users when they follow the link.

### 4.5 Custom theme page queries

If a theme performs a fully custom page query and ignores the normal WordPress menu/page-list APIs, that path is outside normal Core automatic-list protection.

In that case the site/theme must:

- add its own exclusion logic, or
- stop querying private iLungu Club pages directly

This is a theme-specific integration edge case, not a Core contract failure.

## 5. Current Direct-Access Matrix

The following reflects current runtime behaviour in the shared framework.

### 5.1 Private routes that currently deny logged-out direct access

- `my-profile` via `[tpw_member_profile]` — requires a logged-in user and linked member record
- `manage-members` via `[tpw_manage_members]` — logged-out users are denied entirely
- `noticeboard` via `[tpw_noticeboard_list]` — requires login plus an allowed member status, with notice managers retaining their existing management access
- `gallery-admin` via `[tpw_gallery_admin]` — requires login plus gallery-manage authority
- `gallery-help` via `[tpw_gallery_help]` — requires login plus gallery-manage authority
- `flexiclub` via `[flexiclub]` — requires login plus iLungu Club frontend dashboard authority
- `logs` via `[flexiclub workspace="logs"]` — requires login plus iLungu Club frontend dashboard authority
- `menu-management` via `[flexiclub_menu_management]` — requires login plus workspace-specific authority
- `archival-system` via `[flexiclub_archival_system]` — requires login plus workspace-specific authority
- `tpw-control` via `[tpw-control]` — requires TPW Control manage access and section visibility

### 5.2 Noticeboard default

The default iLungu Club Noticeboard is members-only by default.

That means:

- logged-out visitors are denied direct access by the shortcode
- standard viewing requires a logged-in member whose status is allowed by `TPW_Member_Access`
- existing notice-management permissions remain valid for authorised managers and admins even when they are not using the page as an ordinary member viewer

Core keeps Noticeboard in the private-page automatic menu-hiding set.

## 6. Current Product Interpretation

For the listed iLungu Club system and admin-style pages, the current Core direction is:

- `my-profile`, `manage-members`, `noticeboard`, `gallery-admin`, `gallery-help`, `flexiclub`, `logs`, `menu-management`, `archival-system`, and `tpw-control` are private/member-or-admin routes and should deny logged-out direct access
- `member-login` is intentionally public and is not part of the private-page exclusion set

For `noticeboard`, the current default is members-only and remains aligned with the private-page automatic menu-hiding set.

If a future public Noticeboard mode is introduced, it must be documented explicitly before runtime behaviour or automatic menu-hiding is relaxed.

## 7. Post Status Rule

Core must not use WordPress post status changes as the primary privacy mechanism for these pages.

Reasons:

- published pages may still be required for shortcode rendering, routing, and stable URLs
- access varies by logged-in state, member status, and role, not by a simple published/private page state
- hiding a page from lists and denying route access are separate concerns

## 8. Validation Expectations

When changing this area, validate all of the following:

1. logged-out automatic page listings do not expose known private iLungu Club pages
2. direct access still denies logged-out users on private routes
3. explicit site-owned menus are not silently rewritten, except for the Core-managed Members Menu
4. private-page identification does not depend on one specific theme
5. any unresolved route-level gap is documented explicitly rather than implied away
